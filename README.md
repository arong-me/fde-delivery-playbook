## 发现：跟着一条询盘走完整流程

找一条已经处理过的询盘，从收到它到回复客户，逐步记录谁接单、谁查目录、谁能承诺交期。

- **交付物** — 业务走查表：角色、输入、当前步骤、等待／返工点、处理时长。

- **完成条件** — 业务负责人能指出一个值得改善的卡点，并确认基线怎么取。

- **询盘案例** — 把缺规格、同名客户、投诉及确认交期分别标出来。只有规则、负责人和例外说清楚之后，才选第一条可验证路径。

## 定界：让第一版只交付一个结果

把客户想要的自动化拆成可以独立验收的动作。先明确系统在哪一步停下来，什么情况下必须由人接手。

- **交付物** — 范围卡：支持的输入、输出、必填字段、人工接管条件、试点负责人。

- **完成条件** — 给业务人员三条输入，他能独立判定该生成草稿、澄清还是转人工。

- **询盘案例** — 试点只生成待审草稿、澄清问题或人工任务。价格、库存、交期由业务人员确认。

## 实现：把判断、执行和状态拆开

接口负责接收输入，规则或模型产出候选决策，执行层根据权限落记录。把未完成、确认和退回写成显式状态。

- **交付物** — 可运行原型：输入界面、分流函数、审核接口、记录存储及运行说明。

- **完成条件** — 跑一次正常询盘和一次混合投诉，结果与审核动作可查，重启后仍能读取已审记录。

- **询盘案例** — 询盘工作台的在线版与 Node.js API 复用规则，本地用 SQLite 持久化。现阶段候选决策由规则生成。

## 验收：把容易被演示掩盖的问题测出来

先确定预期输出和证据字段，再跑正常、边界及拒绝路径。测试失败时记下错误类型和业务影响，修完加入回归。

- **交付物** — 验收矩阵：输入、预期、实际、证据、严重程度、负责人。

- **完成条件** — 正常路径和高风险异常逐项可复跑；任何漏转人工都能定位到输入及决策记录。

- **询盘案例** — 现有六条为合成规则回归。客户试点再补脱敏样本、人工复核与处理时长基线，分别追踪误转与漏转。

## 试点：先小范围接入，再决定是否扩大

与客户约定测试租户、少量试用人员和退回原流程的条件。先对照人工结果，记录系统和人工各自的处理时间。

- **交付物** — 试点计划：测试账号、数据范围、指标基线、上线范围、暂停条件和回退步骤。

- **完成条件** — 业务和 IT 负责人确认样本、权限与退出条件，试点结果有可追溯记录。

- **询盘案例** — 询盘项目的下一步是接目录与 CRM 测试环境，核对超时、重复提交和人工接管。该步骤属于待验证计划。

## 交接：让没有参与开发的人也能接手

让接手者自己处理一条标准询盘和一条异常。记录在哪里看状态、怎样判断失败、什么时候转给客户负责人。

- **交付物** — 交接包：操作步骤、异常处理、指标看板口径、负责人和下一次复盘时间。

- **完成条件** — 接手者能独立查到运行记录、填写审核说明并导出结果，知道系统出问题时找谁。

- **询盘案例** — 用询盘工作台演练人工审核和导出。正式交付时再补角色权限、监控和使用反馈。
